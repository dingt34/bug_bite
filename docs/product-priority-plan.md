# 虫咬识途：全小程序重点与规划设计

## 一句话定位

在户外发生叮咬、蜇伤或附着后，帮助用户在 3 分钟内知道“现在先做什么、什么时候必须求助、如何留下可用记录”。

“识别虫种、社群经验、路线规划和 AI”都应服务于这句话，而不是与它竞争首页注意力。

## 一、先重新分配产品重点

建议按用户价值而非页面数量分配：

| 重点 | 权重 | 目标 | 首要结果 |
| --- | ---: | --- | --- |
| 事后安全处置 | 45% | 用户遇到问题后马上采取正确行动 | 3 分钟内完成风险分流 |
| 行前预防 | 25% | 出发前降低暴露概率 | 形成地点/活动对应的准备清单 |
| 记录与复查 | 15% | 让用户和医生看到变化 | 事件可追溯、风险可升级 |
| 可信知识与识别 | 10% | 辅助理解，不制造确定性 | 候选提示 + 明确不确定性 |
| 社群与 AI | 5% | 补充经验和问答 | 不影响急救与安全主路径 |

当前最应该压低的是“功能数量”，提高的是“关键路径的完成率”。社区、路线、图鉴、AI 都可以保留，但不应成为第一屏的主行动。

## 二、产品架构：三个场景、一个底层事件

### 场景 A：我现在遇到了问题（最高优先级）

首页 → 危险信号 → 接触类型 → 症状/事实 → 行动建议 → 事件记录 → 复查。

这是产品的主闭环，所有页面都应能回到这个闭环。

### 场景 B：我准备去户外（第二优先级）

目的地/月份/活动 → 暴露风险提示 → 装备清单 → 行程中提醒 → 回家后检查。

路线规划是此场景的工具，不应独立发展成另一个“旅游产品”。路线分享也应作为经历分享中的可选信息。

### 场景 C：我想了解或交流（第三优先级）

图鉴、社群、AI 问答均属于解释和补充层。它们必须带有“经验/候选/非诊断”标签，并提供回到安全处置的入口。

底层统一使用一个 `接触事件`：接触类型、时间、地点、部位、症状、采取措施、图片、风险等级和复查记录。不同场景只是创建或补充同一个事件。

## 三、首页应该只保留四个层级

1. **立即行动**：`我被咬/蜇了，先判断风险`；
2. **单一对象示范**：`疑似蜱附着全流程`，作为新用户理解产品的样板；
3. **行前准备**：`输入目的地，生成准备清单`；
4. **补充工具**：记录、识别、图鉴、社群、AI。

首页不同时强调“识别、路线、社群、AI、图鉴”五个入口。用户在紧张状态下只能快速理解一个主按钮和一个备用按钮。

## 四、功能分级

### P0：必须先稳定

- 危险信号筛查与 120/急诊分流；
- 五类接触事件的最小问答；
- 规则化行动建议；
- 事件保存、摘要复制、复查升级；
- 断网可读的安全卡和本地草稿；
- 隐私说明、图片本地优先保存、云端同步失败重试；
- 统一顶部导航、返回逻辑和空状态。

P0 的验收不是“页面能打开”，而是：用户是否能在没有图片、没有登录、网络不稳定时完成安全路径。

### P1：增强可信度与预防价值

- 行前准备：地区、月份、活动、环境标签；
- 事件图片记录与云端备份；
- 图鉴的对照学习；
- 社群经历结构化字段：地区、接触类型、阶段、是否包含路线；
- 事件与社群发布之间的可选关联。

### P2：在证据和资源充足后再做

- 真实图像识别模型；
- AI 对话的个性化总结；
- 多途径点路线规划；
- 热门路线、排行榜、复杂社群推荐；
- 基于物种/地区的疾病概率或药物建议。

P2 不是不能做，而是必须等 P0 的安全规则、内容审核和数据质量稳定后再做。尤其不能让模型置信度直接影响医疗分级。

## 五、现有页面的重新归位

| 现有页面 | 重新定位 | 设计动作 |
| --- | --- | --- |
| index | 任务分发首页 | 只保留立即处置、行前准备、补充工具三层 |
| danger/contact/guide/result | 事后安全主流程 | 作为第一开发和测试对象 |
| event-detail/event-review/my-events | 个人安全记录 | 强化时间线、复查和摘要 |
| precheck/precheck-result | 行前预防 | 合并成“输入 → 清单 → 回家检查”闭环 |
| route-plan/my-plans | 行程工具 | 从首页降级为行前准备中的二级功能 |
| identify/insect-guide/insect-detail/compare | 可信知识 | 标注候选、不确定性、非诊断；均提供安全判断入口 |
| community/post-publish/post-detail | 经验交流 | 结构化发布，降低点赞/收藏对主流程的干扰 |
| ai | 补充咨询 | 必须显示事件上下文和 Markdown 小卡片，但不替代分流 |
| profile/privacy/login | 信任与数据 | 登录延后到需要云端、社群或备份时 |

## 六、视觉与交互重点

### 安全优先级

- 红色只表示必须立即行动；橙色表示尽快咨询；绿色表示观察记录；
- 每个结果页面先给“现在做什么”，再讲原理；
- 一个页面只保留一个主按钮，次要操作用文字链接或幽灵按钮；
- 复杂说明折叠到“为什么”中，避免用户在紧急状态阅读长文。

### 科学可信度

- 信息旁标记来源等级：`官方指南`、`产品规则`、`用户经历`、`AI 候选`；
- 所有图片识别均使用“疑似/可能/无法判断”；
- 不展示容易被误读为患病概率的精确百分比；
- 结果页显示规则版本和生成时间，便于后续审核。

### 可行性

- P0 的规则用本地数据和本地计算即可运行；
- 图片、云同步、AI 都是可失败的增强服务，不得阻塞安全路径；
- 所有表单支持保存草稿、断点续填和返回不丢失；
- 优先使用现有组件、颜色和导航规范，避免每个页面重新设计一套交互。

## 七、四阶段规划

### 阶段 1：安全闭环（1 个迭代）

只做 P0，选“疑似蜱附着”作为样板，完成危险筛查、症状记录、行动建议、事件复查、离线安全卡。

### 阶段 2：行前预防（1 个迭代）

完善地区/月份/活动规则、准备清单、行程关联和回家后检查；路线只作为行程输入，不扩展社交推荐。

### 阶段 3：可信内容和社群（1 个迭代）

统一图鉴、社群和经历发布的标签；重点解决头像、图片、点赞收藏、返回逻辑和内容审核，不追求复杂推荐。

### 阶段 4：智能增强（评审后）

接入真实识别或 AI 前，先定义模型版本、置信度分级、失败回退、隐私期限和人工审核机制。任何智能结果都只能补充事件，不能替代安全分流。

## 八、建议跟踪的指标

- **首个安全动作完成时间**：进入处置后多久看到并理解下一步；
- **主流程完成率**：危险筛查到结果页的完成比例；
- **危险信号漏选率**：专业人员审查下的高风险案例回放；
- **事件记录与复查率**：保存事件后是否完成至少一次复查；
- **图片误信率**：用户是否把候选当成确诊；
- **离线成功率**：无网络时处置卡和草稿是否可用；
- **社群内容有效率**：包含时间、地点、处理和结果的经历占比。

不要把点赞数、页面停留时间或 AI 对话轮数作为早期核心成功指标，它们可能与安全目标相反。

## 九、最终决策原则

当一个新功能无法回答以下三个问题时，先不进入开发：

1. 它是否帮助用户更快采取安全行动或降低暴露？
2. 它失败时是否不会阻塞主流程或制造错误信心？
3. 它是否能被现有事件模型、内容审核和隐私规则承载？

如果只能选一个方向，优先把“事后安全处置 + 事件复查”打磨成可靠产品，再扩展预防、社群和智能能力。
