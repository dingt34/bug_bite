# 社群评论赞、踩与回复交互调研

更新日期：2026-08-27

## 结论摘要

“虫咬识途”适合采用轻量的二层评论结构：顶层评论负责排序，所有回复收在对应顶层评论下；回复某条回复时，仍展示在同一回复区，通过“回复 @昵称”表达对象。赞与踩应当是同一份用户反应的三种状态，而不是两个互不相关的开关。评论作者可以删除自己的内容，帖子作者或平台执行的管理删除需要使用不同文案。踩只表示“帮助不大”，不能代替举报，也不能作为医疗正确性的判定。

## 一手资料观察

### Reddit

- Reddit 将赞成、反对和撤销定义为同一个投票方向：`1`、`-1`、`0`；再次点击已选箭头等同撤销。这为赞踩互斥提供了直接的数据模型依据。[Reddit 官方 API：vote](https://www.reddit.com/dev/api/#POST_api_vote)
- Reddit 明确表示投票影响内容在社区和讨论中的展示；其社区礼仪将赞定义为“对讨论有贡献”，踩定义为“未贡献或偏题”，而不是简单的“同意/不同意”。[Reddit Help：What are upvotes and downvotes?](https://support.reddithelp.com/hc/en-us/articles/7419626610708-What-are-upvotes-and-downvotes)、[Reddiquette](https://support.reddithelp.com/hc/en-us/articles/205926439-Reddiquette)
- 回复接口通过 `parent` 指向帖子或任意评论，评论读取接口支持评论树和最大深度，说明数据层应保留直接父节点关系。[Reddit 官方 API：comment](https://www.reddit.com/dev/api/#POST_api_comment)、[Reddit 官方 API：comments](https://www.reddit.com/dev/api/#GET_comments_{article})
- 普通用户删除接口只允许删除自己创建的内容；平台管理删除是另一条接口，并明确会对评论做遮蔽和移除。这说明“作者删除”和“审核移除”应当分权并留有不同状态。[Reddit 官方 API：del](https://www.reddit.com/dev/api/#POST_api_del)、[Reddit 官方 API：remove](https://www.reddit.com/dev/api/#POST_api_remove)

### YouTube

- YouTube 在评论操作中同时提供喜欢、不喜欢和回复；回复以线程组织，便于追踪对话。[YouTube Help：View, organize, or delete comments](https://support.google.com/youtube/answer/6000976?hl=en)
- 评论区提供“热门评论”和“最新评论”两种主要排序。这与小程序当前“最赞/最新”的低认知成本方案一致。[YouTube Help：Choose comment settings](https://support.google.com/youtube/answer/9482556?hl=en)
- YouTube 说明点赞和点踩是匿名反馈，且点踩不会通知评论者；不当内容则使用举报与审核工具处理。这支持“踩与举报分离”和“不推送被踩通知”。[YouTube Help：Review & reply to comments](https://support.google.com/youtube/answer/9482367?hl=en)
- 原评论者、频道所有者或平台规则都可能导致评论被移除，体现了作者、内容所有者和平台三类管理边界。[YouTube Help：View, organize, or delete comments](https://support.google.com/youtube/answer/6000976?hl=en)

### 微博（中文平台）

- 微博官方曾将评论区提供为热度与时间两种排序；评论量较大时，热度可主要依据评论点赞，而回复只精选少量露出。其目标是避免低质量回复挤占正文页。[微博新版评论使用指南 2.0](https://weibo.com/ttarticle/p/show?id=2309404032705305146679)
- 微博在列表页精简回复，只保留昵称和正文；完整头像、点赞、时间等信息放在评论详情。这说明小屏列表不宜把每条回复做成与顶层评论同等重量的卡片。[微博新版评论使用指南 2.0](https://weibo.com/ttarticle/p/show?id=2309404032705305146679)
- 微博把不当言论、人身攻击、营销和色情等问题引导到举报菜单；站方识别和博主屏蔽会影响内容展示。[微博新版评论使用指南 2.0](https://weibo.com/ttarticle/p/show?id=2309404032705305146679)
- 微博客服明确用户可删除自己发出的评论，也可删除自己微博下收到的评论，说明前端操作入口可统一放在“更多”菜单，但云端必须按角色校验权限。[微博客服：收到和发出的评论可以删除吗](https://kefu.weibo.com/faqdetail?id=78)

## 推荐交互结构

### 1. 评论卡片

顶层评论保持统一顺序：

1. 头像、昵称、时间和“更多”菜单；
2. 评论正文；
3. `赞  踩  回复` 操作行；
4. 回复摘要或“共 N 条回复，点击查看”。

赞、踩使用同一套线性拇指图标。未选中为灰色；赞选中使用品牌绿色；踩选中建议使用中性深灰或低饱和橙色，不使用警告红色，避免把正常分歧塑造成违规。

删除、举报放入右上角“更多”菜单，避免和高频互动争夺视觉注意力：自己的评论显示“删除”；别人的评论显示“举报”；若帖子作者拥有评论管理权限，可显示“移除评论”，但必须与作者删除分开记录。

### 2. 赞踩互斥

每个用户对每条评论只有一个状态：

| 当前状态 | 点击赞 | 点击踩 |
| --- | --- | --- |
| 无 | 设为赞 | 设为踩 |
| 赞 | 撤销 | 切换为踩 |
| 踩 | 切换为赞 | 撤销 |

建议云端使用唯一约束 `(authorOpenid, commentId, targetType)`，反应记录保存 `vote: 1 | -1`；无反应时删除记录或保存 `0`。切换必须在同一个事务中完成，不能先减旧计数、再异步增加新计数。否则网络重试可能造成重复记录或计数漂移。

公开展示建议分别显示赞数与踩数，或只显示赞数并保留踩状态。若采用综合分，定义为 `score = likeCount - dislikeCount`，不要把赞踩相加称为“热度”。被踩不发送通知。

### 3. 回复层级

数据层保留：

- `rootCommentId`：所属顶层评论；
- `parentCommentId`：实际回复的评论；
- `replyToUserId` 和 `replyToNickname`：被回复对象；
- `depth`：用于校验与迁移，不直接决定无限缩进。

界面只展示两层。回复顶层评论和回复其他回复都进入同一回复区，后者显示“昵称 回复 @对象”。这样既保留真实关系，又避免微信小程序窄屏出现三层以上缩进。

顶层评论按用户选择排序；同一顶层评论下的回复固定按时间正序。默认只露出 2 条回复，超过后显示“展开其余 N 条回复”。点击回复后，输入框提示“回复 @昵称”，发送成功后保持当前线程位置。

### 4. 排序

只提供两个入口：

- **最新**：`createdAtTimestamp DESC, _id DESC`；
- **最赞**：`score DESC, createdAtTimestamp DESC, _id DESC`。

最后使用 `_id` 作为稳定兜底，避免相同时间或相同分数时列表跳动。回复数不建议直接加入“最赞”分数，否则互相灌水的长线程容易压过简洁、有效的建议。医疗相关社群也不应将高赞解释为医学结论。

### 5. 删除策略

- 评论无回复：作者删除后可物理删除，并清理赞踩记录。
- 评论已有回复：推荐软删除，正文显示“该评论已删除”，清空头像、昵称快照、正文及其他个人信息，保留节点和子回复关系。
- 管理员或帖子作者移除：显示“该评论因违反社群规范已被移除”或更中性的审核文案，并保留后台审计字段；不要伪装成作者主动删除。
- 被删除评论不能继续点赞、踩或回复；已有回复可阅读，但新的回复应指向仍有效的上级评论。

微博官方当前产品会连带删除下方回复，但“虫咬识途”更适合占位保留：用户的回复可能含有独立的护理经验，级联删除会误删他人内容。此处是结合小程序场景作出的产品取舍，不是对微博行为的复制。

## 医疗安全边界

1. 点踩是相关性或帮助度反馈，不是医疗审核，不因踩数达到阈值自动删除。
2. 举报独立提供“危险医疗建议、辱骂骚扰、广告营销、隐私泄露、其他”原因；危险医疗建议应进入较高优先级审核队列。
3. 顶层评论与回复都必须执行同等的文本安全检查、长度限制、频率限制和登录校验；安全服务失败时不应直接放行公开发布。
4. 云函数必须验证评论属于当前帖子、父评论与根评论属于同一帖子、被回复用户确实来自父评论，不能信任客户端传入的昵称或归属关系。
5. 删除、投票和回复接口应支持幂等或请求标识，避免微信弱网重试产生重复回复和计数漂移。
6. 评论区显著保留“经验分享不替代专业诊疗”；疑似严重症状仍引导紧急求助，不以评论热度作为行动建议依据。

## 建议的最小实现范围

本轮建议先实现：

1. 评论三态赞踩与原子切换；
2. 二层视觉回复、任意评论可作为回复对象；
3. 顶层“最新/最赞”，回复按时间正序；
4. 自己删除、他人举报和有回复时的删除占位；
5. 评论与回复共用内容安全、限流和权限校验。

暂不实现复杂热度算法、无限层级、作者置顶、勋章、图片回复和回复排序。这些功能会显著增加信息密度和审核成本，但对当前小程序的核心价值有限。
